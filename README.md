## 项目简介

做一套温湿度采集的东西。DHT11 拿数据，OLED 上显示，同时通过串口发给电脑。

目的不是做出产品，是把采集、显示、通信这三块串起来跑通。后面换传感器、换通信方式，这套工程可以直接复用。

## 踩坑记录

### 1. 编译报 #268：变量声明写在了可执行语句后面

- **现象**：`error: #268: declaration may not appear after executable statement in block`，指向 `GPIO_InitTypeDef GPIO_InitStructure;` 这一行
- **原因**：ARMCC 默认按 C90 标准编译，C90 要求一个函数里的变量声明必须写在所有可执行语句之前。我把声明写在了 `RCC_APB2PeriphClockCmd(...)` 后面
- **解决**：Options for Target → C/C++ 勾上 C99 Mode，然后保存工程（Ctrl+S），设置才会写进 `.uvprojx`；或者把声明提到 `main` 函数第一行，不依赖任何编译选项
- **收获**：ARMCC 默认按 C90 编译，C90 要求变量声明写在同一个块里所有可执行语句之前。改代码比改选项更可靠——选项只在当前工程生效，代码拿到哪都能编

### 2. 下载连不上目标：Debug 里的 Port 没选 SW

- **现象**：ST-Link 已插上电脑，但下载 / 调试连不上目标芯片
- **原因**：Debug → Settings 里 Port 选的是 JTAG，而板子和 ST-Link 之间只接了 SWD 那两根线（SWDIO / SWCLK），JTAG 当然连不上
- **解决**：Port 改成 SW，Debug Adapter 里立刻出现 IDCODE `0x1BA01477`（ARM CoreSight SW-DP），连接恢复正常
- **收获**：接了什么线，软件里就选什么口；SWD 只用两根线就能下载 + 调试

### 3. L6218E: Undefined symbol OLED_Init —— .c 没加进工程

- **现象**：`main.c / LED.c / Key.c / Serial.c` 全部编译 0 error，到链接阶段报 `L6218E: Undefined symbol OLED_Init` 和 `OLED_ShowString`，`Target not created`
- **原因**：`main.c` 里 `#include "OLED.h"` 只拿到**声明**，编译能过；但 `OLED.c` 没被加进 Keil 工程，没有 `oled.o` 提供**定义**，链接器找不到对应的 `T`
- **解决**：Project 窗口右键 `Hardware` 组 → Add Existing Files → 选 `OLED.c` → Rebuild
- **收获**：编译过 ≠ 能链接。声明只让编译过；定义必须参与编译（`.c` 在工程里），链接器才找得到。**文件在磁盘上，不等于在工程里**

## 技术要点

### GPIO 输出模式：推挽 vs 开漏

点灯用的是**推挽输出**（`GPIO_Mode_Out_PP`）。它和开漏的区别说到底就一句：**推挽上下都有主动通路，开漏只有下面那一条。**

| | 推挽 Push-Pull | 开漏 Open-Drain |
|---|---|---|
| 内部结构 | 上管（接 VDD）+ 下管（接 GND） | 只有下管 |
| 输出高 | 上管导通，引脚直连 VDD | 下管关断，引脚悬空，靠外部上拉电阻 |
| 输出低 | 下管导通，引脚直连 GND | 下管导通，引脚直连 GND |
| 驱动能力 | 高、低电平均为低阻抗，两个方向都出力 | 只有低电平有力，高电平由外部电阻决定 |
| 典型用途 | 驱动 LED、普通输出 | I2C 总线、多设备共线、电平转换 |

**为什么推挽驱动能力强**：输出高时引脚通过上管直接连到 3.3V，输出低时通过下管直接连到 0V，两条都是低阻抗通路。电流出得来、也进得去，且电平摆幅是满幅的。

**为什么 I2C 必须用开漏**：总线上挂多个设备，如果都用推挽，一个输出高（接 VDD）、一个输出低（接 GND），就成了电源对地短路。开漏只能拉低、不能拉高，多个设备「谁拉低谁赢」，不会打架——这叫**线与**。

参考限值（数据手册绝对最大值）：STM32F103 单个 I/O 灌/拉电流 **25mA**，整颗芯片所有 I/O 流出、流入的总和各不超过 **150mA**。

### 单总线为什么必须用开漏（DHT11）

I2C 用开漏的原因上面说了；DHT11 这种**单总线**（1-Wire）是同一套逻辑，但值得单独记一笔——它是「两个设备分时驱动同一根线」的典型。

**推挽是「主动输出高/低」，开漏是「只能主动拉低，高靠上拉」。**

假设 MCU 和 DHT11 都用推挽：

```
MCU 输出高                    DHT11 输出低
   VDD                            │
    │                          [NMOS] 导通
 [PMOS] 导通                      │
    │                            GND
    └──────── 同一根线 ───────────┘
```

电流路径：`VDD → MCU 的 PMOS → 导线 → DHT11 的 NMOS → GND`，中间**没有限流电阻**，只有两个管子的导通内阻（各几十欧）。3.3V / 几十欧 ≈ 几十 mA，超过 GPIO 的 25mA 上限——轻则波形烂掉，重则烧管子。

换成开漏 + 10k 上拉：

```
              VDD
               │
             [10k]        ← 唯一的限流点
               │
        ───────┴─────── 总线
        │              │
     [NMOS]         [NMOS]
     MCU 释放        DHT11 拉低
     (高阻)          (导通)
        │              │
       GND            GND
```

- MCU 写 1 = **松开**（高阻，不参与）
- DHT11 拉低 = 把线拉到 GND
- 电流：`VDD → 10k → DHT11 的 NMOS → GND`，约 **0.33mA**，安全

**「谁拉低谁赢」**：只要有一个设备把线拉低，线就是低；其他松开的设备看到低也不会去抢——因为它们根本没在驱动高。逻辑上就是**线与**：

```
总线电平 = 设备A输出 AND 设备B输出 AND ...
```

**落到 DHT11 代码上**：

- 引脚配 `GPIO_Mode_Out_OD`（不是 `Out_PP`）
- 数据线必须外接 **10k 上拉到 3.3V**（开漏自己拉不高）
- `DHT11_OUT(1)` = **释放总线**（不是「输出 3.3V」），`DHT11_OUT(0)` = 拉低
- 主机拉低 ≥18ms 发起始信号，靠的就是「主动拉低」；释放后的高电平，是 10k 上拉给的

一句话：**一条线上只有一个驱动者（LED）→ 推挽随便用；一条线上有多个驱动者（I2C / DHT11）→ 必须开漏，否则两个司机一个踩油门一个踩刹车，芯片就废了。**

### PC13 的特殊限制：蓝板为什么是低电平点亮

查 STM32F103x8 数据手册，PC13 / PC14 / PC15 这三个脚有一条专门注解，原文：

> PC13, PC14 and PC15 are supplied through the power switch. Since the switch only sinks a limited amount of current (3 mA)... the speed has to be limited to 2 MHz... and these I/Os must not be used as a current source (e.g. to drive an LED).

翻译过来三条限制：① 由备份域经内部电源开关供电，电流能力只有 3mA 级别；② 输出速度上限 **2MHz**；③ **不能当电流源用（不能靠它驱动 LED）**。

那蓝板上的灯为什么能亮？因为蓝板的接线是**灌电流**（sink）方式：

```
3.3V ──[限流电阻 ~1kΩ]── LED阳极 → LED阴极 ── PC13
```

PC13 输出低时，电流从 3.3V 经电阻、LED 流入引脚再入地。**这里 PC13 是在「吸」电流，不是在「供」电流**，正好绕开了第 ③ 条限制。输出高时两端都是 3.3V，没有压差，灯灭。

所以「PC13 低电平点亮」不是软件习惯，是**硬件接线决定的**——换成「引脚→LED→地」的接法，就变成高电平点亮了。

> 这条限制只针对 PC13 / PC14 / PC15。代码后来把 LED 换到了 **PA0**——PA0 是普通 I/O，没有这个 2MHz 上限，也就能正常拉到 50MHz。踩过这个限制，再看到「换到普通 I/O 就没事」时，就知道是为什么了。

### 编译与链接：.o / U / T / 链接器

一句话：**`.h` 公布名字，`.c` 实现名字，`.o` 各自打包，链接器按名字拼成整机。**

`.h` 里放的是**声明**（`void LED_Init(void);`），`.c` 里放的是**定义**（带函数体）。`#include` 不是「连接」，是**预处理阶段的文本复制**——把 `.h` 的内容贴到 `.c` 里。

每个 `.c` 单独编译成一个 `.o`（目标文件）。`.o` 里有一张**符号表**：

- `U`（Undefined）：这个文件**要用、但自己没有**的函数
- `T`（Text/Defined）：这个文件**自己定义**的函数

链接器把工程里所有 `.o` 摊开，按名字把 `U` 和 `T` 配对：

```
main.o   [U: LED_Init, OLED_Init, Key_GetNum]   ← 我要这些
led.o    [T: LED_Init, LED1_ON, LED2_TURN]      ← 我有这些
oled.o   [T: OLED_Init, OLED_ShowString]        ← 我有这些
key.o    [T: Key_Init, Key_GetNum]              ← 我有这些
                    ↓  链接器按名字配对
                 object.axf
```

- 找不到配对 → `L6218E: Undefined symbol`（有 U 没 T）
- 同一符号两份定义 → `L6200E: Multiply defined`（有两份 T）

Keil 点一次 Build，内部走五步：

| 阶段 | 谁干的 | 输入 → 输出 |
|---|---|---|
| 预处理 | 预处理器 | `.c` + `.h` → `.i`（宏展开、include 复制） |
| 编译 | 编译器 | `.i` → `.s`（汇编） |
| 汇编 | 汇编器 | `.s` → `.o`（目标文件） |
| 链接 | 链接器 armlink | 多个 `.o` + 库 → `.axf` |
| 转换 | fromelf | `.axf` → `.hex` / `.bin` |

所以 `.c` 永远不能被 `#include`——那样 `main.o` 和 `led.o` 会各有一份定义，链接时报重复定义。
